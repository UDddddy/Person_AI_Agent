## 二、可观测性增强：MetricsCollector

### 2.1 和 ObservabilityExtension 的分工

| | ObservabilityExtension（阶段5） | MetricsCollector（阶段9） |
|---|---|---|
| 输出形式 | 每条事件打印一行 JSON | 聚合后输出一份报告 |
| 用途 | 实时流水（debug 用） | 汇总视图（监控/评估用） |
| 粒度 | 单条事件 | 统计指标（次数/平均值/总和） |
| 类比 | 服务器的 access log | 服务器的监控仪表盘 |

两者互补，不重复。一个看"发生了什么"，一个看"整体怎么样"。

### 2.2 收集哪些指标

```python
report = {
    "tool": {
        "total_calls": 3,           # 工具调用总次数
        "by_name": {"calculator": 2, "get_current_time": 1},  # 按工具名分布
        "avg_latency_s": 0.0117,    # 平均延迟
        "max_latency_s": 0.02,      # 最大延迟
    },
    "llm": {
        "total_calls": 2,           # LLM 调用总次数
        "with_tool_calls": 1,       # 其中带工具调用的次数
        "avg_latency_s": 1.15,      # 平均延迟
        "max_latency_s": 1.5,       # 最大延迟
    },
    "token_usage": {
        "prompt_tokens": 300,       # 输入 Token
        "completion_tokens": 80,    # 输出 Token
        "total_tokens": 380,        # 总 Token（可换算成本）
    },
}
```

### 2.3 为什么 LLM 层用独立的 bus

工具层的事件走 `composition_root` 创建的 bus（pipeline 内部 emit），LLM 层的事件走 `graph_agent` 模块级的 `llm_bus`。

为什么不共用一个 bus？
- 工具层 bus 是在 `create_pipeline()` 里创建的，生命周期和 pipeline 绑定
- LLM 调用在 `call_llm()` 里，拿不到 pipeline 的 bus（agent_node 是纯函数，没有 pipeline 引用）
- 两个 bus 分离更清晰：工具事件和 LLM 事件是不同层的关注点

MetricsCollector 支持 `subscribe_bus()` 多次调用，可以同时订阅多个 bus，所以分离不影响聚合。

### 2.4 给事件加 latency 的改动

- `pipeline.py`：`tool_result` 事件加 `latency` 字段（之前只有 name 和 result）
- `graph_agent.py`：`call_llm` 加 `time.perf_counter()` 计时，emit `EVENT_LLM_RESULT` 带 latency 和 usage

这是"埋点"的典型做法——在关键路径的起止点计时，通过事件把耗时传出去。

## 三、评估框架：EvalRunner

### 3.1 评估什么

四个维度：
1. **任务成功率**：输出是否满足期望（工具选对 + 关键词命中）
2. **工具选择正确率**：LLM 返回的 tool_calls 是否是期望的工具
3. **延迟**：每次 LLM 调用耗时
4. **Token 成本**：总 Token 用量

### 3.2 为什么做组件级评估而非端到端

EvalRunner 直接调 `provider.chat(messages, tools=TOOL_SCHEMA)`，不跑完整的 LangGraph 图。

原因：
- **更精确**：直接测"LLM 工具选择能力"，排除图执行、工具执行等干扰因素
- **更轻量**：不需要启动图、不需要会话存储，一次调用就是一个用例
- **更可控**：用 ScriptedProvider 可以精确控制 LLM 返回，测试评估逻辑本身

如果要端到端评估（完整图 + 真实工具），可以在 EvalRunner 基础上扩展，但组件级是基础。

### 3.3 EvalCase 设计

```python
@dataclass
class EvalCase:
    name: str
    user_input: str
    expected_tool: str = ""          # 期望工具名；空=期望不调工具
    expected_keywords: list[str] = []  # 期望输出包含的关键词
```

通过条件：`工具正确 AND 所有关键词命中`。两个条件独立判断，报告里分别展示，方便定位失败原因。

### 3.4 评估报告

```
评估报告：5 个用例
  成功率：3/5 (60.0%)
  工具选择正确率：80.0%
  平均延迟：0.000s
  总 Token：225
  [PASS] 计算任务  工具: 期望=calculator 实际=calculator ✓
  [FAIL] 工具选错  工具: 期望=get_current_time 实际=calculator ✗
```

人类可读 + 结构化数据（EvalSummary）双输出，既可以看报告，也可以程序化处理。

## 四、Docker 化

### 4.1 Dockerfile 设计要点

```dockerfile
FROM python:3.11-slim          # 轻量基础镜像
ENV PYTHONDONTWRITEBYTECODE=1  # 不生成 .pyc
ENV PYTHONUNBUFFERED=1         # stdout 不缓冲（日志实时可见）
COPY requirements.txt .        # 先装依赖（层缓存）
RUN pip install -r requirements.txt
COPY . .                       # 再复制代码
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**关键：依赖层缓存**。先 COPY requirements.txt 并安装，再 COPY 代码。这样代码变更时 Docker 不会重装依赖，构建速度从分钟级降到秒级。

### 4.2 .dockerignore

排除 `.venv/`、`.env`、`*.db`、`test/`、`docs/`、`.git/` 等。
- `.env` 不打进镜像（密钥通过 env_file 运行时注入）
- `*.db` 不打进镜像（运行时生成）
- `test/` `docs/` 运行时不需要（减小镜像体积）

### 4.3 docker-compose

```yaml
services:
  api:
    build: .
    ports: ["8000:8000"]
    env_file: [.env]
    healthcheck:
      test: ["CMD", "python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health')"]
```

- `env_file`：运行时注入 `.env`（LLM_API_KEY 等）
- `healthcheck`：调用 `/health` 端点，自动检测服务是否就绪

### 4.4 为什么 SQLite 不需要单独容器

会话存储用 SQLite（文件型数据库），不需要 PostgreSQL/Redis 容器。这是学习项目的刻意选择——**零外部服务依赖**，一个容器就能跑起来。

生产环境如果需要高并发，可以把 SQLite 换成 PostgreSQL，但那是另一个话题。

## 七、设计哲学一句话总结

> **可观测性是"知道发生了什么"，评估是"知道做得好不好"，容器化是"让别人也能跑"，文档是"让别人看得懂"——这四件事把"能跑的代码"变成"可交付的项目"。**

三个可迁移到任何项目的通用能力：
1. **埋点+聚合分离**：事件逐条上报（流水）+ 指标聚合统计（汇总），两者互补
2. **组件级评估优先**：先测单个组件的正确性，再考虑端到端，更精确更轻量
3. **依赖层缓存**：Docker 构建时把依赖和代码分层，代码变更不重装依赖

## 八、面试题

### 基础题

**Q1：ObservabilityExtension 和 MetricsCollector 有什么区别？**
> 参考：前者逐条打印 JSON 日志（实时流水，debug 用），后者聚合统计指标（汇总视图，监控用）。一个看"发生了什么"，一个看"整体怎么样"。互补不重复。

**Q2：你的评估框架评估哪些维度？怎么评估的？**
> 参考：四个维度——任务成功率（工具正确+关键词命中）、工具选择正确率（LLM 返回的 tool_calls 是否是期望工具）、延迟（每次 LLM 调用耗时）、Token 成本（总用量）。做组件级评估，直接调 provider.chat，不跑完整图，更精确更轻量。

**Q3：Dockerfile 为什么先 COPY requirements.txt 再 COPY 代码？**
> 参考：利用 Docker 层缓存。requirements.txt 不变时，依赖层不会重建，代码变更时构建速度从分钟级降到秒级。这是 Docker 最佳实践。

### 设计题

**Q4：如果要给 Agent 加一个"平均响应时间 P99"指标，你怎么设计？**
> 参考：在 MetricsCollector 里加一个 latencies 列表，report 时排序取第99百分位。或者用 HDRHistogram 等专业直方图数据结构（内存更高效）。当前实现只有 avg/max，P99 需要保留所有延迟数据。

**Q5：评估框架怎么处理"LLM 输出不确定"的问题？同一个用例可能这次过下次不过？**
> 参考：几种思路——①多次运行取平均（降低随机性影响）；②用 LLM-as-judge（让另一个 LLM 评判输出质量，比关键词匹配更灵活）；③用 MockProvider 固定输出（测评估逻辑本身，不测 LLM 能力）；④设置容忍阈值（比如 80% 通过率算通过）。

**Q6：你的项目用 SQLite，生产环境够吗？怎么迁移？**
> 参考：SQLite 适合低并发、单节点场景。学习项目刻意选择零外部依赖。生产环境如果需要高并发或多实例，可以把 session_store 抽象成接口（当前是直接操作 SQLite），加一个 PostgreSQL 实现，通过配置切换。Compaction 和 session_adapter 层不需要改。

### 深入题

**Q7：MetricsCollector 是内存聚合的，服务重启后指标就丢了，怎么解决？**
> 参考：几种方案——①定期把 report 写入数据库或文件（持久化）；②接入 Prometheus（专业时序数据库，MetricsCollector 只负责 expose 指标）；③用 Redis 做共享存储（多实例聚合）。当前实现是单进程内存版，适合学习和单机部署。

**Q8：如果要做"持续评估"（每次代码变更后自动跑评估并对比），你怎么设计 CI 流程？**
> 参考：①把评估用例固化到 test/ 或 eval/ 目录；②CI 里跑 pytest + EvalRunner；③把评估结果（成功率/延迟/Token）写入文件或上传到 dashboard；④和基线对比，退化超过阈值则 fail。当前 EvalRunner 已经输出结构化的 EvalSummary，可以直接被 CI 脚本解析。

**Q9：Docker 容器里的 SQLite 数据会丢失吗？怎么持久化？**
> 参考：容器删除后数据会丢失（SQLite 文件在容器内部）。解决方式：①用 volume 挂载数据库文件所在目录（`volumes: ./data:/app/data`）；②或者把数据库路径配置化，指向挂载目录。当前 docker-compose 没有加 volume，是因为学习项目可以接受数据丢失；生产部署必须加。

### 场景题

**Q10：线上 Agent 突然变慢了，你怎么用你项目里的可观测性工具排查？**
> 参考：①看 MetricsCollector 报告——LLM 平均延迟是否升高？工具延迟是否升高？②看 ObservabilityExtension 的逐条日志——哪次调用特别慢？③看 token_usage——是否 prompt_tokens 暴涨（可能是上下文没压缩，历史太长）？④如果是 LLM 延迟高，可能是模型服务问题；如果是工具延迟高，可能是某个工具卡住了；如果是 token 暴涨，检查 compaction 是否正常工作。

**Q11：让你给这个项目加一个"成本控制"功能（每月 Token 不超过预算），你怎么设计？**
> 参考：①MetricsCollector 已经在统计 token_usage，可以加一个 BudgetGuard 扩展，订阅 EVENT_LLM_RESULT，累计 token 超过预算时拦截（用 HookRegistry 的拦截型钩子）；②预算存在配置或数据库里，按月重置；③拦截时返回"本月预算已用完"而不是静默失败。这复用了阶段5的 Hooks 体系和阶段9的指标体系。
