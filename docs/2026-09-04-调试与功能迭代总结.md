## 1. 问题一：点击旧会话，聊天框一片空白

### 1.1 现象

侧边栏会话目录显示正常（来自 localStorage），但点击任意旧会话后，
消息区域永远是"开始对话"的空状态引导页。

### 1.2 根因（两层缺陷叠加，缺一不会复现）

1. **前端从不取历史**：`loadSession()` 只做了三件事——重置 `state`、改标题、
   重建空状态 DOM。会话列表存在 `localStorage['agent_sessions']` 里，但每条
   只存 `{id, title, time}`，**消息内容从来没存过，也从来没向后端要过**。
2. **后端没有历史出口**：`/api/chat` 是 POST 聊天接口，树形存储
   （`sessions.db`，阶段 6 的 append-only 存储）里明明存着全部消息，
   却没有任何 GET 接口能把它读出来。

### 1.3 为什么会出现这个问题

这是**架构演化过程中的"半成品接缝"**，而不是谁的低级失误：

- 项目按阶段推进，阶段 6 引入树形存储时，优先保证的是"写路径"正确
  （每轮 `build_chain` 重建历史 → 图执行 → `persist_messages` 追加），
  读路径当时只有 `build_chain` 内部用，没有暴露成 API 的需求；
- 前端 `index.html` 是独立写的，会话列表用 localStorage 自己造了一套
  最小实现——它能"列出"会话（有 id/title 就够了），但列不出"内容"；
- 两边各自闭环、都在自己的阶段验收通过，**接缝处没人验收**。
  这也是集成类 bug 的典型产生模式：单侧都有测试，组合行为无测试。

### 1.4 怎么解决的

**后端**（`app/main.py`，v0.3.1）新增一个只读端点：

```python
@app.get("/api/sessions/{session_id}/history")
def session_history(session_id: str):
    init_store()                      # 幂等建表，防御性
    chain = build_chain(session_id)   # 从叶子回溯到根，天然有序
    # user/assistant/tool → {role, content, tool_calls?, tool_call_id?}
    # system / compaction / fork 内部节点过滤，不返回给前端
```

**前端**（`web/index.html`）`loadSession()` 末尾追加 `await loadHistory(id)`：
先建 `tool_call_id → 结果` 映射，再按 role 渲染气泡；
旧后端 404 或网络异常时静默降级，保持空状态不报错。

### 1.5 为什么这么改（设计决策）

- **为什么过滤 system/compaction/fork**：`system` 是 LLM 上下文不是对话内容；
  `compaction` 是压缩摘要节点（给 LLM 看的）；`fork` 是分支元数据。
  前端展示只需要 user/assistant/tool 三类对话事实——数据模型里"给 LLM 的"
  和"给人看的"本就该分离。
- **为什么前端要按 `tool_call_id` 配对**：树形存储里工具调用发起
  （assistant.tool_calls）和结果（tool 条目）是**两个独立 entry**，
  这是 append-only 模型的固有结构，配对逻辑必须有人做——放在前端
  渲染层做，后端保持"忠实返回链上原始事实"的薄接口风格。
- **为什么空会话返回 `{"count": 0}` 而不是 404**：会话不存在和会话为空
  对前端来说行为一致（显示空状态），用一个 200 统一处理，减少分支。

### 1.6 验证

- 新增 `test/test_history_api.py`：完整链回放、内部节点过滤、空会话 3 用例；
- 实测真实数据：`arch_verify_0904` 库里 7 条 entry 返回 6 条（system 正确过滤）、
  48 条长会话全量返回、工具配对信息完整。

## 2. 问题二：流式输出"先打一遍工具原始结果，再接 AI 总结"

### 2.1 现象

流式模式下，气泡开头先原样出现工具返回值
（如 `2026-09-04 17:47:10`），紧接着才是正式回答
（"现在是 2026年9月4日 17:47:10。"）。用户观察为"对话两三次之后就会出现"。

### 2.2 根因（两层，第二层是修第一层时实测暴露的）

**第一层：对 `stream_mode="messages"` 语义的误解。**
`stream_graph_events` 的循环把每个产出物的 `.content` 都当 token 推给前端：

```python
for msg_chunk, _metadata in compiled.stream(..., stream_mode="messages"):
    content = getattr(msg_chunk, "content", None)
    if content:
        yield ("token", content)     # ← ToolMessage 的 content 也会走到这
```

但 `stream_mode="messages"` 的真实语义是：**产出图执行期间写入 state 的
所有新增消息**——不只 LLM 的 token 增量（AIMessageChunk），还包括 tools
节点执行完写入的**完整 ToolMessage**。于是工具原始输出被当成一条 token
推给前端，和后续回答拼在同一气泡里。

**第二层：provider 是非流式实现。**
第一版修复用 `isinstance(msg_chunk, AIMessageChunk)` 过滤，结果端到端实测
**连回答都没了，只剩 done 事件**——因为自定义 provider 非流式调用，
图里产出的是整条 `AIMessage` 而非 `AIMessageChunk`，全被过滤。

### 2.3 为什么会出现

- **语义偏差**：`stream_mode="messages"` 的直觉理解是"流式输出 LLM 消息"，
  实际是"流式输出所有新增消息"。这类"API 名字暗示的语义"与"真实语义"
  的偏差，是最常见的框架使用误区——而且它**不报错**，只是多推了不该推的
  内容，属于静默行为类 bug。
- **"两三次之后才出现"的错觉**：不是按轮次算的，是**凡触发工具的轮次必现**。
  纯聊天不调工具就看不到，用户前几轮恰好没触发工具，形成"偶尔出现"的印象。
- **第一版修复踩坑的原因**：复现时看到的输出是两条"完整消息"（一条
  ToolMessage + 一条 AIMessage），而不是逐 token 流。这本身就说明 provider
  非流式——但当时先按标准姿势（只认 Chunk）修了，实测才发现。
  **教训：修复"过滤什么"之前，先确认"流里到底有什么"。**

### 2.4 怎么解决的

双重过滤 + 事件分流（`app/stream_graph.py`）：

```python
for msg_chunk, metadata in compiled.stream(..., stream_mode="messages"):
    node = (metadata or {}).get("langgraph_node")
    if node == "tools" and isinstance(msg_chunk, ToolMessage):
        yield ("tool_result", {"name": ..., "content": ...})  # 独立事件，不混 token
        continue
    if node != "agent":                       # 防线1：按产出节点过滤
        continue
    if not isinstance(msg_chunk, (AIMessage, AIMessageChunk)):  # 防线2：按类型
        continue                              # 两种都放行：兼容流式/非流式 provider
```

### 2.5 为什么这么改

- **为什么双重过滤**：节点过滤（`langgraph_node`）是主防线，类型过滤是
  双保险——防止未来图里新增节点时又漏。两个条件各自单独成立，互为冗余。
- **为什么 ToolMessage 转成 `tool_result` 事件而不是直接丢弃**：前端需要
  "开始 → 结束"的闭环才能渲染时间线（见问题四）；丢弃信息不如结构化输出。
- **为什么 `AIMessage` 和 `AIMessageChunk` 都放行**：provider 抽象层
  （阶段 7）允许非流式实现，过滤条件必须对两种实现都成立——这也顺手
  修复了另一个隐藏 bug：完整 `AIMessage` 没有 `tool_call_chunks`，
  导致 `tool_call` 事件**此前从未真正触发过**，前端流式里从没显示过工具卡片。

### 2.6 验证

修复前后 SSE 事件流对比（实测）：

```
修复前: token("2026-09-04 17:52:07") → token("现在是 **...**")        ← 泄漏
修复后: tool_call({name,args}) → tool_result({name,content}) → token → done
```

新增 `test/test_stream_filter.py`：含"tools 节点产出 AI 消息也必须过滤"
的双保险用例（FakeCompiled 模拟 LangGraph 的 `(chunk, metadata)` 产出）。

## 3. 任务三：增加工具 / 插件 / MCP 服务的三条路径

用户提出扩展需求后，先摸清现有架构的扩展点，再把三条路径全部落地：

| 路径 | 接入点 | 已落地内容 |
|------|--------|-----------|
| ① 自定义工具 | `BaseTool` 子类 → `registry.py` 注册 | `tools/hash_text.py`（含必填+enum 参数的示例），LLM 实测自主调用成功 |
| ② 插件/扩展 | 阶段 5 的 `EventBus`/`HookRegistry`/`ExtensionManager` | 骨架与接入点说明（`composition_root.manager.register()`） |
| ③ MCP 服务 | `tools/mcp_bridge.py`（新写） | stdio + streamable http 双传输、配置驱动、可选启用 |

**为什么 MCP 能无痛桥接（核心洞察）**：本项目的 `TOOL_SCHEMA` 是 OpenAI
function-calling 格式，其 `parameters` 就是 JSON Schema；MCP 工具的
`inputSchema` 同样是 JSON Schema——**两边天然同构，字段直接映射**，
不需要经过 LangChain 工具体系转换。这也是没用 `langchain-mcp-adapters`
的原因：项目不用 LangChain 原生 ToolNode 绑定，自研桥接更贴合架构、少一层依赖。

**工程细节**：
- 映射函数 `mcp_tool_to_base_tool()` 是纯函数（可离线测试，不依赖 mcp 包），
  用 pydantic 官方 `create_model` 动态生成 `BaseTool` 子类（v2 下比 `type()` 稳）；
- `registry.py` 的 MCP 启用块双重保护：没有 `mcp_servers.json` 不动；
  有配置但没装 `mcp` 包只提示跳过，不影响启动；
- 每次调用新建 MCP 会话（connect → initialize → call → close），学习项目
  取简，注释中标注生产环境应改长连 + 重连。

## 4. 任务四：工具调用时间线（线性显示每次工具调用）

### 4.1 需求与设计

前端显示模型具体调用了哪些工具，按调用顺序**线性**排列。
设计为三层贯通的数据流：

```
ToolPipeline.execute()          ← 唯一执行入口，天然保序
  └→ trace[]: {name, args, result, latency, blocked}
       ├→ 普通模式: run_graph_agent_detailed() → ChatResponse.tool_trace
       └→ 流式模式: tool_call{name,args} → tool_result{name,content} 事件对
             └→ 前端时间线: 流式逐步渲染 / 普通整段渲染 / 历史回显聚合渲染
```

### 4.2 关键决策与理由

- **为什么 trace 记在 pipeline 而不是图节点里**：`pipeline.execute()` 是所有
  工具执行的唯一出口（普通/流式/HITL 三条链路共用），在这里记录天然保序、
  天然全覆盖，且拦截（审批拒绝）、参数缺失也如实记为 `blocked`。
- **为什么拆 `run_graph_agent_detailed()` 而不是改 `run_graph_agent` 签名**：
  旧函数被 150+ 测试和其他模块引用，返回 str 改 dict 是破坏性变更。
  新函数返回 dict、旧函数一行包装——**扩展不改契约**。
- **为什么时间线放气泡外**：旧版工具卡片塞在 AI 气泡**内部**，而流式 token
  到达时 `bubbleEl.textContent = fullText` 会**覆盖掉卡片**——这是本次发现的
  又一个隐藏 bug（旧版流式里工具卡片几乎不可见的原因）。时间线挂到
  `.message-content` 顶部、文本气泡之前，两者互不干扰。
- **为什么历史回显要"聚合"**：树形存储里一轮多工具循环是
  `assistant(tc) → tool → assistant(tc) → tool → assistant(文本)` 的扁平链，
  逐条渲染会把步骤分散在多个气泡里。聚合策略：连续的"发起调用+结果"
  归入同一条时间线，直到出现带文本的 assistant 才是最终回答气泡。

### 4.3 前端视觉

左侧竖线 + 节点圆点的时间线样式：**橙色呼吸灯 = 执行中 → 绿色 = 完成 →
红色 = 被拦截**；等宽字体展示参数/结果，超 500 字截断。

### 4.4 验证

- 新增 `test/test_tool_trace.py` 3 用例：pipeline 顺序记录（成功/不存在/缺参）、
  API 响应带完整 trace、纯聊天空 trace；
- 实测流式事件序列：`tool_call{含参数}` → `tool_result{含结果}` → `token` → `done`。

## 5. 踩坑记录（工程教训）

### 5.1 同一文件并行 Edit 竞态

给 `main.py` 同时改"加 import"和"bump 版本号"两处时并行提交了两个编辑，
第二个写回时覆盖了第一个的修改——import 行丢失，测试报 `NameError`。
**教训：同一文件的多处编辑必须串行执行**；工具返回"成功"只代表写入成功，
不代表合并正确。

### 5.2 测试桩要忠实模拟真实产出结构

FakeCompiled 最初 `yield` 裸消息对象，而真实 LangGraph 产出
`(chunk, metadata)` 元组 → `ValueError: too many values to unpack`。
**教训：mock 之前先确认被 mock 方的真实输出形状**（和问题二第二层根因
是同一类错误：对"流里到底有什么"想当然）。

### 5.3 pytest 临时目录与沙箱的冲突

pytest 的 `tmp_path` 工厂在运行数次后会自动清理旧临时目录，删除操作被
沙箱拦截导致整个测试命令被拒；随后复用同一 `--basetemp` 又引发 fixture
目录污染（37 个 error）。
**最终策略：每次全量运行用全新子目录 `--basetemp=./.pytest_tmp/run<N>`，
既不触发删除，也不互相污染。**

## 7. 认知沉淀（三条最值得记住的结论）

1. **"流里到底有什么"先于"过滤什么"**：`stream_mode="messages"` 产出的是
   图内所有新增消息而非 LLM token——修复过滤 bug 前先 dump 一份真实事件流，
   再决定过滤条件（本轮先用裸 isinstance 踩坑，后用 metadata+类型双保险收敛）。
2. **架构演化的 bug 都长在"接缝"上**：写路径和读路径各自验收通过，组合行为
   无测试 → 历史空白；LLM 上下文和前端展示共用一条链 → 内部节点泄漏。
   每引入一条新数据通路，就要同时问"谁读它、谁不该读它"。
3. **扩展不改契约**：`run_graph_agent_detailed()` 包裹旧函数、`trace` 并列于
   `logs`、`tool_trace` 作为新增可选字段——三次扩展全部以"叠加 + 兼容包装"
   完成，161 个旧测试零改动。破坏性变更是最后手段。
